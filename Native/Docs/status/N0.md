Found while stitching:
- **Fixed — `JobQueue.wait(for:)` could return before the job's row was written.** `complete()` set the final status in
  memory and then awaited the run-closing write and the job row; a `wait` arriving in that window (actor reentrancy)
  returned at once, so a reader of the `job` table could still see `running`, and a waiter registered in the window was
  never resumed (it timed out). Seen once as a failure of "a failed task: status failed …" in the final quick run. A
  record is now `settled` only once persisted; `wait` returns early only for a settled record, waiters are collected
  after persistence, and an unsettled record is never pruned. ScrollsJobsTests then passed 3 / 3 runs and every later gate.
- **Test fixed — "memory: only one job with a peak above 256 MB".** It sampled the process-wide
  `MemoryBudget.reservedBytes` once, while other suites' jobs (now including the engine self-test's) held transient
  reservations; it now waits up to 5 s for transient ones to go (a leaked reservation never goes, so a leak still fails).
- **Fixed — no job could start in the simulator.** `MemoryBudget.availableBytes()` read `os_proc_available_memory()`,
  which is 0 in the iOS simulator (no jetsam limit), so every job waited for memory forever. The simulator now uses the
  Mac's rule (physical memory minus footprint); a device still reads `os_proc_available_memory()`. Measured before and
  after with `-selftest probe` (`jobs.cancel.*` rows: "did not start within 10 s" → 0.8 ms and 0.27 ms).
- **Finding for the lead (§1.4, §3.8) — SQLite's mmap cap on iOS.** The iOS 27 simulator runtime's SQLite reports
  `MAX_MMAP_SIZE=20971520` (20 MB); the Mac's is 1 GB, and §1.4 plans 256 MB per reader. If the device's library has the
  same cap, readers get 20 MB of mmap each (results unchanged, page-cache reads instead). The probe reports it as a
  warning; the device row records it (queued). No code assumes the larger window.
- **For R (from N0a):** `viewstate.mjs` and `format.mjs` look keys up in plain objects, so `Object.prototype` names leak
  through (`lg=…~toString~` keeps a lineage type `toString`, `tg=constructor1` is dropped silently, `refWords('constructor:1')`
  prints a function). Proposed RF: `Object.hasOwn` or a `Map`. Swift treats these keys as unknown; no golden contains them.
